# 28. 숙소 최저가 비교 — 상세 설계

- 상태: **설계 상세화** (사용자 확인 전 구현하지 않음)
- 날짜: 2026-11-09 (초안) → 2026-11-09 (A+B+D+E 혼합으로 다시 정리)
- 요청: 숙소 이름·체크인·체크아웃을 넣고 검색하면 국내외 숙소 예약 앱 3곳 이상(아고다·트립닷컴·여기어때·NOL 등)의
  가격을 한 번에 비교해서 보여 준다. 참고: 아고다스캐너(https://agodascanner.com).
  **무한 검색 요청이 생기지 않도록 방어 코드와 오류 시 검색 중단은 필수**
- 확정된 것: **Q1 방식 = A+B+D+E 혼합, 아고다스캐너처럼** (사용자 결정 2026-11-09)

## 1. 목표와 범위

| 한다 | 하지 않는다 |
|---|---|
| 한 숙소·한 날짜 조건의 **예약 앱별 가격** 비교 (B·D) | 지역 전체 숙소 목록 검색 (숙소 찾기는 지도·AI 추천 몫) |
| **아고다 경로별 가격** 비교 (E, 아고다스캐너 방식) | 예약·결제 대행, 가격 저장, 가격 변동 기록 |
| 가격을 못 가져온 앱도 **바로 검색 링크** (A) | 로봇 확인(CAPTCHA) 풀기·우회, 프록시 돌리기, 브라우저 위장 |
| 버튼을 누를 때만 1회 검색, 한도·차단기로 자동 중지 | 정기 자동 조회(가격 알림)는 이번 범위 밖 (§12) |

## 2. 아고다스캐너 분석 (참고 모델, 2026-11-09 페이지 코드 확인)
- **입력:** 아고다 숙소 링크 하나. 폼은 `GET /result?url=<아고다 링크>` → **주소로 바로 열 수 있다**
- **실제 동작:** 결과 화면 스크립트에 **가격을 받아 오는 요청이 없다** (`fetch` 0개, 썸네일 이미지 요청만).
  아고다 링크의 **접속 경로 값(CID)** 을 미리 정해 둔 값으로 바꾼 **링크 23개**를 만들어 보여 줄 뿐이다
  - 검색 경유 7개 (구글 지도 3·구글 검색 3·네이버 검색 1)
  - 카드사 13개 (국민·우리·BC·신한·토스·하나·마스터·비자 등, 일부는 카드사 전용 페이지 링크)
  - 항공사 3개 (대한항공·아시아나·에어서울 적립)
  - 그 밖에 카드·결제 프로모션 페이지 링크 묶음
- 가격은 사용자가 링크를 하나씩 눌러 **아고다 화면에서** 본다. 그래서 23개여도 아고다스캐너 서버는 요청을 하지 않는다
- 아고다는 들어온 경로·결제 수단·회원 여부에 따라 값을 다르게 보여 주는 동적 가격이라 경로마다 가격이 다를 수 있다
- **수익:** 프로모션 링크에 제휴 태그(`tag=`)가 붙어 있고 광고·분석 스크립트가 있다. 우리는 **제휴 태그·추적을 넣지 않는다**
- **결론:** 경로 비교는 **링크 방식으로 충분**하다. 우리 서버가 아고다에 요청할 필요가 없어 차단·약관 위험이 없고,
  경로 수에 한도를 둘 이유도 없다 (§4.3)
- **카드 할인 주의:** 카드사 경로 가격은 그 카드로 결제해야 적용되는 경우가 많고, 원화 결제는 이중환전 수수료(3~8%)가
  붙을 수 있다 → 화면에 짧은 안내로 보여 준다 (§7.3)

## 3. 전체 구조

```
[웹] 숙소 최저가 시트 ── 버튼 1번 = POST /api/lodging/prices 1번 ──▶ [홈 서버]
                                                                     │
          ┌──────────── 예산·한도·차단기 검사 (§8) ─────────────────┤
          │                                                           │
          │  ① 숙소 확인 (이름 → 각 앱 숙소 id, 30일 캐시)            │
          │  ② 소스별 가격 수집 (동시에 최대 2개, 마감 20초)          │
          │      B 구글 호텔(SerpApi)  : 예약처별 가격               │
          │      E 아고다 숙소 찾기   : 숙소 주소 1번 (링크 있으면 0)  │
          │      D 트립닷컴·여기어때·NOL : 각 앱 직접 조회            │
          │  ③ 합치기: 1박·총액 맞추기, 이상한 값 버리기, 최저가      │
          └───────────────────────────────────────────────────────────┘
                                                                     │
[웹] ◀── 소스별 결과 + 소스별 상태(성공/시간 초과/중지/차단) ──────────┘
     + A 바로 검색 링크는 웹에서 직접 만든다 (서버 호출 없음, 오프라인 가능)
```

- **소스 = 어댑터 하나.** 소스마다 같은 틀(`identify` → `prices`)을 따르고, 한도·차단기·예산을 소스마다 따로 둔다.
  한 소스가 고장 나도 다른 소스는 그대로 보인다
- 결과는 **한 번의 응답**으로 준다 (폴링·자동 재요청 없음). 마감 20초가 지나면 끝난 소스만 담아 돌려준다
- A는 늘 보인다: 가격을 못 가져온 앱, 서버가 멈춘 경우, 오프라인일 때의 대안

## 4. 소스별 설계

### 4.1 A — 바로 검색 링크 (웹, 무료, 호출 0)
- `domain/lodgingLinks.ts` 순수 함수: (숙소 이름, 체크인, 체크아웃, 인원) → 앱별 검색 주소
- 대상(안): 여기어때 · NOL · 아고다 · 트립닷컴 · 부킹닷컴 · 구글 호텔 (Q2)
- 주소 모양은 구현 때 앱마다 실제로 열어 확인하고, 날짜가 안 들어가는 앱은 "날짜는 앱에서 다시 골라요" 표시
- 휴대폰에 앱이 깔려 있으면 앱으로 열릴 수 있다 (유니버설 링크). 안 깔려 있으면 웹으로
- 테스트: 주소 만들기 단위 테스트 (특수 문자·한글 이름·1박/여러 박)

### 4.2 B — 구글 호텔 가격 (SerpApi `google_hotels`)
- 호출 1: `q=숙소 이름 + 도시`, `check_in_date`, `check_out_date`, `adults`, `currency=KRW`, `gl=kr`, `hl=ko`
  → 숙소 후보와 `property_token`
- 호출 2 (필요할 때만): `property_token`으로 상세 → 예약처별 가격 `prices[]` (부킹닷컴·아고다·트립닷컴·호텔스닷컴 등)
- **한 번 검색에 최대 2번.** 첫 호출에서 숙소가 바로 잡히면 1번으로 끝날 수도 있다 (실제 응답으로 확인)
- 무료: 월 250회(시간당 50). 결제 수단을 연결하지 않으면 넘을 때 막힐 뿐 과금 없음 → `group: 'free'`
- 키: 서버 `.env` `SERPAPI_KEY` (갱신일 메모 포함). 웹 번들에 넣지 않음

### 4.3 E — 아고다 경로별 링크 (아고다스캐너 방식, 요청 0)
- **흐름:** 숙소 이름·날짜 입력 → ① 아고다 숙소 주소 얻기 → ② 웹이 CID만 바꾼 경로별 링크를 전부 만든다 →
  사용자가 눌러 아고다에서 가격 확인. ②는 순수 함수(`domain/agodaRoutes.ts`)라 **서버 요청 0, 오프라인 가능**
- **경로 수: 제한 없음.** 아고다스캐너와 같은 23개 이상 (검색 경유·카드사·항공사 + 카드 프로모션 페이지).
  경로 목록은 공개 자료로 모아 사용자 확인 후 웹 데이터 파일에 넣는다. 제휴 태그는 넣지 않는다
- **① 아고다 숙소 주소 얻기** (위에서부터 먼저 되는 것):
  1. **아고다 링크 붙여넣기** — 사용자가 아고다 앱·웹에서 공유한 링크. 요청 0, 가장 정확
  2. **예약에 저장된 아고다 링크** 재사용 — 요청 0
  3. **자동 찾기** — 서버가 아고다 숙소 검색(자동완성) **1번**으로 숙소 id를 찾아 날짜를 넣은 주소를 만든다.
     30일 캐시. 아고다에 보내는 것은 숙소 이름뿐 (§4.5 원칙, 하루 100번 상한, 막히면 멈춤). 사전 점검(§11) 필요
  4. 자동 찾기가 안 되면 **아고다 검색 결과 링크에 CID를 넣은 것**으로 대신 (숙소를 한 번 더 눌러야 함). 점검 필요
- **날짜·인원:** 주소의 `checkIn`·`los`(박 수)·`adults`·`rooms`를 입력값으로 맞춘다
- **결과:** 묶음별(검색 경유·카드사·항공사) 링크 목록. 카드사 경로에는 "그 카드로 결제할 때" 안내
- **가격을 앱 안에 보이게 하려면** 서버가 경로마다 아고다에 요청해야 한다 (경로 23개 = 요청 23번, 차단 위험).
  이번에는 하지 않는다. 가격 표시는 B(구글 호텔)의 아고다 가격 1줄로 대신한다
- **점검할 것:** 아고다가 처음 들어온 경로를 쿠키로 기억해서 두 번째 링크부터 경로가 안 바뀌는지 확인.
  그렇다면 "링크마다 새 시크릿 창" 같은 안내를 붙인다

### 4.4 D — 예약 앱 직접 조회 (트립닷컴 · 여기어때 · NOL)
- 앱마다 어댑터 1개: `identify(이름, 도시) → 숙소 id` (자동완성·검색 1회), `prices(id, 날짜, 인원) → 가격` (1회)
- **한 앱당 한 번 검색에 최대 2번**, 결과 페이지 넘기기 없음
- 대상은 사전 점검(§11)에서 일반 요청으로 응답이 오는 앱만. 막히는 앱은 A 링크로만 남긴다
- 부킹닷컴·호텔스닷컴은 B(구글 호텔)에 보통 들어 있으므로 D 대상에서 뺀다 (요청 수 줄이기)
- 국내 앱(여기어때·NOL)은 국내 숙소에서 쓸모가 크고, 해외 숙소는 상품이 적을 수 있다 → 여행지가 해외면 기본 꺼짐(Q4)

### 4.5 직접 조회(D·E) 공통 원칙
- **정직한 요청만:** 일반 브라우저처럼 보이게 하는 위장, 프록시·IP 돌리기, 로봇 확인 풀기, 로그인 쿠키 사용 **안 함**
- 막히면 **멈춘다** (우회하지 않는다). 막힌 소스는 A 링크로 대신한다
- 사이트에 부담 주지 않기: 소스마다 하루 요청 상한(§8.3), 6시간 캐시, 같은 조건 동시 요청 합치기
- 이용약관상 자동 수집을 막는 사이트가 있을 수 있다 → 위험을 문서로 남기고 **사용자가 받아들인 소스만** 켠다 (ADR, §10)
- 위험: 집 PC IP가 그 사이트에서 차단될 수 있다 (집에서 그 사이트를 쓸 때도 영향). 차단 신호 시 24시간 중지로 줄인다

## 5. 숙소 확인 (같은 숙소 찾기)
- 입력이 이름뿐이면 앱마다 숙소 이름이 다르게 적혀 있다 (영문·한글·지점명)
- **정규화:** 소문자, 공백·기호 제거, "호텔/hotel/by/앤" 같은 흔한 말 빼고 비교, 도시 힌트(여행지·예약의 주소)
- **고르기:**
  - 후보가 1개거나 1등이 확실하면 자동 선택
  - 애매하면 B 결과의 후보 3개를 보여 주고 "이 숙소가 맞나요?" (고르면 그 다음에 E·D 진행 → 버튼 1번 더)
- **캐시:** (정규화 이름 + 도시) → 앱별 숙소 id, **30일**. 사용자 정보 없이 숙소 정보만 저장
- 예약 탭 숙소에서 열면 이름·주소·날짜·인원이 채워진다. 숙소 예약에 아고다 링크가 있으면 그것을 먼저 쓴다

## 6. 가격 맞추기 (비교할 수 있게)
- 공통 모양: `{ source, label, nightly, total, currency, taxIncluded: true|false|null, url, note }`
- **1박/총액:** 둘 다 주면 둘 다, 하나만 주면 박 수로 계산하고 "계산" 표시
- **세금:** 포함 여부를 모르면 "세금 확인" 표시. 최저가 순위는 같은 기준(세금 포함 총액)끼리 먼저, 모르는 것은 뒤에
- **통화:** KRW로 요청. 다른 통화로 오면 기존 환율(수출입은행) 값으로 환산하고 "환산" 표시
- **이상한 값 버리기:** 숫자 아님·0 이하·통화 없음·다른 가격들 중앙값의 1/5 미만 또는 5배 초과 → 버리고 기록만
- 응답 검사는 zod 스키마 (`packages/shared/src/schemas/lodgingPrice.ts`)로. 모양이 다르면 그 소스는 "실패"

### 7.3 상태·문구 (한 줄 = 한 문장, 22자 안쪽)

|---|---|
| 검색 중 | 버튼 "찾는 중…" 잠금 + 소스 이름 옆 작은 원 (진행 표시만, 추가 요청 없음) |
| 일부만 성공 | 성공한 것만 표, 나머지는 "가져오지 못했어요" + [찾기] 링크 |
| 시간 초과 | "시간이 오래 걸려 멈췄어요" |
| 소스 중지(차단기) | "잠시 쉬는 중이에요\n링크로 찾아 주세요" |
| 오늘 한도 | "오늘 검색을 다 썼어요\n내일 다시 할 수 있어요" (버튼 잠금) |
| 서버 꺼짐·오프라인 | 가격 영역 숨김, A 링크만 + "연결되면 가격도 보여요" |
| 카드사 경로 | "그 카드로 결제할 때 가격이에요" |
| 결제 통화 | "원화 결제는 수수료가 붙을 수 있어요" (아고다·해외 앱 결과 아래 1줄) |

- 결과는 기기에 6시간만 보관(같은 조건으로 다시 열면 바로 보임, 호출 0). 서버 DB에는 저장하지 않음 (§8.2 캐시만)

## 8. 무한 검색 방지 · 오류 시 중단 (필수)

### 8.1 화면 (웹)
| 방어 | 내용 |
|---|---|
| 누를 때만 | 입력·시트 열기·화면 이동으로 자동 검색 없음. `useEffect` 안에서 검색 호출 금지 (코드 리뷰 체크) |
| 잠금 | 검색 중 버튼 잠금 + 진행 중 요청이 있으면 새 요청을 만들지 않음 (모듈 단위 1개) |
| 재사용 | 같은 조건(이름·날짜·인원·소스 구성)은 6시간 기기 캐시 결과를 보여 주고 서버 호출 안 함 |
| 재시도 없음 | 실패해도 자동 재시도 0번. 사용자가 다시 누르는 것만 |
| 연타 막기 | 1분에 3번 넘게 누르면 1분 잠금 |
| 시간 제한 | 요청 시간 제한 25초 (서버 마감 20초 + 여유) + 시트를 닫으면 `AbortController`로 취소 |
| 서버 거절 | 429·503·507 응답은 남은 시간까지 버튼 잠금 (`retryAfter`를 따름) |

### 8.2 서버 — 요청 입구
| 방어 | 내용 |
|---|---|
| 로그인 | `requireUser` 필수. 여행 id를 받으면 멤버십 확인 (인가 누락 테스트 포함) |
| 입력 검사 | 이름 1~80자, 날짜 형식·체크아웃 > 체크인·최대 30박·오늘 이후·1년 이내, 인원 1~8 |
| 사람별 한도 | **분당 3회 · 하루 30회** (Q6). 넘으면 429 + `retryAfter` |
| 전체 동시 실행 | 서버 전체에서 검색 **동시에 2개까지**. 넘으면 503 "잠시 뒤 다시" |
| 결과 캐시 | 같은 조건은 **6시간** 서버 메모리 캐시 (사용자 구분 없이 공유, 사용자 id 없음). 같은 조건 동시 요청은 하나로 합침 |
| 마감 | 검색 1번 전체 마감 **20초**. 넘으면 끝난 소스만 돌려주고 나머지 취소 |
| 전체 끄기 | `.env` `LODGING_PRICE_SOURCES=links,serpapi,agoda,tripcom,yeogi,nol` 로 소스 켜고 끄기 + 관리자 화면 끄기 버튼 |

### 8.3 서버 — 소스별 예산
| 소스 | 검색 1번당 외부 요청 | 하루 상한 (`apiUsage`) | 비고 |
|---|---|---|---|
| B `serpapi_hotels` | 최대 2 | 월 250 (95%에서 자동 중지) | 시간당 50은 사람별 한도로 충분히 아래 |
| E 경로 링크 | **0** (웹에서 링크만 만듦) | — | 경로 수 제한 없음 |
| E `agoda_lookup` (숙소 자동 찾기) | 최대 1 (링크가 있으면 0) | 하루 100 | 30일 캐시 |
| D `tripcom_direct` | 최대 2 | 하루 60 | |
| D `yeogi_direct` | 최대 2 | 하루 60 | |
| D `nol_direct` | 최대 2 | 하루 60 | |
| **합계** | **최대 9** | | 반복문으로 페이지를 넘기지 않음. 요청 수는 코드에서 상수로 상한 |

- 모든 외부 요청은 `guardApi`(허용 여부) → 요청 → `trackApi`(기록) 순서. 새 id를 `APIS`에 등록 (D·E는 `group: 'free'`, 스스로 정한 `freeDaily`)
- 요청 하나하나에 시간 제한 **8초**, 응답 크기 상한 **2MB**, 리다이렉트 최대 2번, 다른 도메인으로 가는 리다이렉트 거부

### 8.4 서버 — 소스별 차단기 (오류 시 중단)
| 신호 | 동작 |
|---|---|
| 연속 실패 3번 (시간 초과·5xx·모양 다름) | 그 소스 **30분 중지** |
| **차단 신호** — 403·429, 로봇 확인 페이지, 알 수 없는 리다이렉트 | 그 소스 **24시간 중지** + 관리자 화면 경고. 진행 중인 그 소스 요청도 즉시 중단 |
| 일주일에 차단 신호 3번 | 그 소스 **자동 끄기** — 관리자가 다시 켤 때까지 |
| 응답 모양이 바뀜 (스키마 실패 5번 연속) | 그 소스 끄기 + "사이트가 바뀐 것 같아요" 경고 (고칠 때까지) |
| SerpApi 무료량 95% | `guardApi`가 막음 → 그 달 B 중지 (과금 없음) |

- 차단기 상태는 서버 메모리 + `api_usage` 표에 기록해서 재시작해도 이어진다
- 중지된 소스는 호출하지 않고 바로 "잠시 쉬는 중"으로 응답 (요청 0)

### 8.5 테스트 (CI에서 실제 외부 호출 없음)
- 순수 함수: 정규화·숙소 고르기·가격 맞추기·이상값 버리기·링크 만들기
- 서버: 사람별 한도, 전체 동시 2개, 캐시·합치기, 마감 20초, 소스별 예산 상한, 차단기 3단계(30분·24시간·자동 끄기), 인가 누락
- 어댑터: 저장해 둔 응답 예시(fixture)로 읽기 테스트. 차단 페이지 예시로 "차단 신호" 판정 테스트
- 웹: 버튼 1번 = 요청 1번, 검색 중 다시 눌러도 요청 없음, 실패 후 자동 요청 없음, 시트 닫으면 취소 (Vitest + Playwright)
- 실제 호출 확인은 임시 `apps/server/test/zz-live.test.ts`에서만, 끝나면 지운다

## 10. 개인정보·약관·문서
- 외부로 보내는 것: 숙소 이름, 도시, 날짜, 인원, 통화뿐. 사용자 정보·좌표·여행 이름은 보내지 않는다
- 보내는 곳: SerpApi(구글 호텔), 아고다, 트립닷컴, 여기어때, NOL — 서버에서만. 웹이 직접 부르지 않음

- 기록(로그)에는 사용자 id와 숙소 이름을 함께 남기지 않음 (횟수만)
- **새 ADR-0010 "숙소 가격 조회"**: ADR-0004 범위 밖 외부 전송 + 직접 조회(D·E) 위험 수용을 기록
- 개인정보 처리방침·데이터 출처 페이지에 위 곳들 추가. 화면에 "가격은 각 앱 기준이고, 최종 가격은 앱에서 확인"

## 14. 단계 (단계마다 사용자 확인 후 다음으로)
1. **틀 + A**: 실험실 `lodgingPrice`, 시트·입력·A 링크, 화면 쪽 방어(잠금·연타·취소), 서버 입구(한도·동시 실행·캐시·차단기·예산) 빈 소스로
2. **사전 점검**(§11) → 결과 보고, 켤 소스 결정 + ADR-0010
3. **B 구글 호텔** 어댑터 + 숙소 확인 + 가격 맞추기
4. **E 아고다 경로 링크** (경로 목록 사용자 확인 후) + 아고다 숙소 자동 찾기 — 링크 부분은 서버 없이 1단계와 함께 해도 됨
5. **D 직접 조회** (통과한 앱만, 앱마다 커밋 1개)
6. 관리자 화면 소스 상태·끄기 버튼, 개인정보 처리방침 갱신
