# 18. 예약 자동 채우기 설계 (초안 — 사용자 확인 전 구현 금지)

> 2026-10-25 사용자 요청: "KKday·Klook·네이버·카카오·NOL·여기어때·아고다 등에서 예약 정보를 직접 불러올 수 있는지 확인하고, 예약 부분을 자동으로 채울 수 있게".
> 결정이 필요한 것은 §6에 모았다.

## 1. 조사 결과 — 예약 내역을 "직접 불러오는" API는 없다

| 서비스 | 고객 본인 예약 조회 API | 비고 |
|---|---|---|
| KKday | 없음 | 공개 문서 없음. 업체용 B2B(Rezio)만 |
| Klook | 없음 | 공개 API는 **상품을 파는 업체·채널용**(OCTO 표준: 상품·재고·예약 만들기). 제휴(어필리에이트)는 판매 수수료용 링크·피드 |
| 아고다 · Booking.com · 에어비앤비 | 없음 | 모두 **판매 제휴용** API. 고객 예약 읽기 API 없음 |
| 네이버 예약 | 없음 | "예약 관련 API는 제공하지 않음"(네이버 커머스 API 답변 2023). 사업 제휴 심사로만 |
| 카카오 | 없음 | 카카오 로컬·지도 API에 예약 기능 없음 |
| 야놀자 NOL · 여기어때 | 없음 | 개발자 공개 API 없음. 제휴 계약으로만 |
| Gmail에서 예약 메일 읽기 | 가능하나 **사실상 불가** | Gmail 읽기 권한은 Google "제한 범위" — 공개 앱은 보안 심사(유료 외부 평가)가 필요. 무료 원칙에 어긋남 |

결론: 서비스에 로그인해 예약을 가져오는 방식은 **어느 곳도 제공하지 않는다**.
대신 모든 서비스가 공통으로 주는 것 — **예약 확인 메일·문자·확인 페이지의 글**, 일부는 **캘린더(.ics) 첨부** — 를 받아 채우는 방식이 현실적이다 (TripIt 등도 같은 방식).

## 2. 제안: 3가지 입력 통로 + 기기 안에서 읽기

### 2.1 붙여넣기로 채우기 (모든 기기)

```
예약 추가
┌──────────────────────────────────────────┐
│ 📋 확인 메일·문자 붙여넣기로 채우기        │  ← 예약 추가 맨 위
└──────────────────────────────────────────┘
 → 붙여넣기 칸 → [읽기]
 → "아고다 예약으로 보여요. 아래 칸을 채웠어요 (확인해 주세요)"
   종류: 숙소 / 이름: 신주쿠 그레이스리 호텔 / 체크인 11.08 15:00 / 체크아웃 11.10 11:00
   예약번호: 1234567890 / 주소·연락처 …   ← 바뀐 칸은 강조
```

### 2.2 공유해서 채우기 (안드로이드 설치 앱)

- 메일 앱·문자·KKday 앱에서 **[공유] → 트립포켓** 하면 위 화면이 바로 열린다 (PWA Web Share Target, 무료·라이브러리 없음)
- 아이폰은 공유 대상 등록을 지원하지 않아 붙여넣기만 (iOS 제약)

### 2.3 캘린더 파일(.ics) 가져오기

- 항공사·호텔 메일에 붙는 `.ics`(일정 초대)를 파일로 고르면 날짜·시간·장소·제목을 채운다

### 2.4 읽는 방법 (기기 안에서, 서버로 보내지 않음)

1. **사이트 알아보기**: 보낸 곳·문구로 사이트 판별 (agoda, kkday, klook, myrealtrip, 네이버 예약, 야놀자/NOL, 여기어때, 대한항공·아시아나·제주항공 e-티켓 등 한국인 많이 쓰는 10여 곳)
2. **사이트별 규칙**: "체크인", "Check-in", "예약번호", "Booking ID", "픽업 장소" 같은 라벨 다음 값을 읽는 규칙 (사이트마다 작은 규칙 파일, 실제 메일 샘플로 시험)
3. **일반 규칙**(모르는 사이트): 날짜·시간·예약번호 모양·전화·주소·인원 추출
4. 못 읽은 칸은 비워 두고 사용자가 채운다 — **항상 저장 전에 확인 화면**

- 예약 메일에는 이름·전화·결제 정보가 있어 **기기 밖으로 보내지 않는 것이 기본** (CLAUDE.md "사용자 데이터는 홈 서버 외로 전송 금지")
- 선택(§6-3): 규칙으로 못 읽을 때만 "AI로 읽기" — 이름·전화·카드번호를 가린 뒤 무료 AI(Gemini 등)로. 사용자가 누를 때만

## 3. 채우는 칸 (종류별)

| 종류 | 채우는 칸 |
|---|---|
| 항공 | 편명·출발/도착 공항·날짜·시간·터미널·좌석·예약번호(PNR) |
| 숙소 | 이름·체크인/체크아웃 날짜·시간·주소·연락처·객실·예약번호·결제 메모 |
| 픽업·드랍 | 예약 사이트·날짜·시간·인원·타는 곳·내리는 곳·편명·기사 연락처 |
| 투어·티켓 | 상품명·날짜·시간·인원·집합 장소·예약번호 |
| 음식점 | 이름·날짜·시간·인원·연락처 |

## 4. 화면·코드

- `features/bookings/ImportSheet.tsx` (지연 로딩) — 붙여넣기·파일·공유로 받은 글
- `domain/bookingImport/` — `detectSite()`, 사이트별 `parse<Site>()`, `parseGeneric()`, `parseIcs()` (순수 함수 + 단위 테스트, 메일 샘플은 개인정보를 지운 가짜로)
- `manifest.webmanifest`에 `share_target` 추가, 서비스 워커가 받은 글을 앱으로 넘김
- 새 의존성 없음, 첫 화면 크기 영향 없음(가져오기 화면만 지연 로딩)

## 5. 한계

- 사이트가 메일 양식을 바꾸면 규칙도 고쳐야 한다 → 규칙이 실패해도 일반 규칙으로 일부는 채움, 사용자 제보로 보완
- 사진(캡처)만 있는 예약은 이번 범위 밖 (글자 인식 라이브러리는 크고 무거움 — 원하면 별도 결정)

## 6. 확인이 필요한 결정

1. 통로: 붙여넣기 + 공유(안드로이드) + .ics — 셋 다(추천) / 붙여넣기만 먼저
2. 처음 지원할 사이트 목록: 아고다·KKday·Klook·마이리얼트립·네이버 예약·NOL(야놀자)·여기어때·대한항공·아시아나·제주항공 (추천) — 더하거나 뺄 곳?
3. 규칙으로 못 읽을 때 **"AI로 읽기"(개인정보 가린 뒤 무료 AI로 보냄)** 를 둘까요? (추천: 두되 사용자가 누를 때만) / 기기 안에서만
4. 사이트별 규칙을 맞추려면 **실제 확인 메일 샘플**이 필요해요 — 개인정보를 지운 메일 글을 몇 개 주실 수 있나요? (없으면 공개된 양식 예시로 시작)
